# 6.5 MTP 与投机验证调度

> 书外内容。原书第 7 章讨论了投机解码，3.4、3.5 节已经介绍了原理、草稿的几种来源和 K 的选择。本节讨论大规模部署中的投机解码：模型自带的草稿模块，以及在高并发下怎样决定验证多少草稿。模拟实验是书外内容。

3.5 节的结论是：投机解码用空闲的算力换取更少的前向次数，并发高时算力不再空闲，收益就会缩小甚至变负。但近两年的大模型部署几乎都开着投机解码，DeepSeek-V4.1-Flash 的 DSpark、GLM、Qwen3-Next 的 MTP 都是例子。这一节讨论它们怎样在高并发下仍然有收益。

## 1. 草稿的三种来源

| 来源 | 例子 | 草稿开销 | 接受率 | 需要额外训练 |
|---|---|---|---|---|
| 独立的小模型 | Qwen3-0.6B 为 Qwen3-32B 起草 | 中 | 中 | 不需要，但要同一个分词器 |
| 附加的草稿头 | Medusa、EAGLE-3 | 低 | 较高 | 为每个目标模型训练 |
| 模型自带的 MTP 层 | DeepSeek-V3、GLM-4.5、Qwen3-Next | 低 | 高 | 随预训练一起训练 |

MTP 层与模型一起预训练，见过同样多的数据，与目标模型的分布最接近。DeepSeek-V3 报告，它的 MTP 模块预测的第二个 token 接受率为 85% 到 90%，decode 速度约提高到 1.8 倍。对推理系统来说，MTP 层"免费"：模型发布时就带着，不需要另找或另训草稿头。

DeepSeek-V4.1-Flash 的 DSpark 更进一步。根据第三方解读，它用三个小的 Transformer 块一次前向预测之后 5 个位置，并带有一个**置信度头**，估计每个草稿被接受的概率。DeepInfer 的 README 说，由置信度估计来安排什么时候做验证。

## 2. 为什么需要置信度

固定草稿长度 $K$ 有两个问题：

1. **内容差别很大**。抄写代码、复述上下文时，草稿几乎全部被接受；开放式的叙述中，第二个草稿就常被拒绝。同一个 $K$ 对前者太短，对后者太长。
2. **最优的 $K$ 随负载变化**。batch 小时 GPU 受带宽限制，多验证几个 token 几乎不花时间；batch 大时 GPU 受算力限制，每个被拒绝的草稿都白白占用了计算。

有了置信度，就可以**逐个序列、逐步**决定验证多少：沿着草稿往后，累计置信度（各位置估计的接受概率之积）低于阈值就停下。有把握的序列多验证，没把握的少验证甚至不验证。阈值则可以随负载调整：空闲时低，繁忙时高。EAGLE-2 的动态草稿树也利用了类似的信号（3.5 节）。

## 3. 模拟

`code/stage6/mtp_sim.py` 用 Roofline 估算验证的耗时（8B 模型，H100），比较固定 $K$ 与按置信度决定两种策略。下面是 batch 为 1、64、256 时的部分结果：

```bash
python code/stage6/mtp_sim.py
```

```text
batch = 1
  策略            吞吐（相对）  每步产出  每步验证
  固定 K = 3          2.47       2.69      4.00
  固定 K = 5          2.82       3.24      6.00
  置信度 ≥ 0.3        2.72       2.96      3.96

batch = 64
  固定 K = 2          2.02       2.29      3.00
  固定 K = 3          1.79       2.69      4.00
  置信度 ≥ 0.5        2.02       2.50      3.05

batch = 256
  不用投机            1.00       1.00      1.00
  固定 K = 1          0.87       1.72      2.00
  置信度 ≥ 0.85       0.91       1.55      1.63
```

三个结论：

- **每步验证的 token 数相同时，按置信度挑选产出更多**。batch 1 时，置信度 ≥ 0.3 与固定 $K = 3$ 验证的 token 数相同（约 4 个），每步产出 2.96 对 2.69，多出约 10%。
- **最优的 $K$ 和阈值随 batch 变化**。batch 1 时 $K$ 越大越好；batch 64 时最优的 $K$ 降到 2；batch 256 时连 $K = 1$ 都不划算。
- **batch 大到 GPU 受算力限制后，投机解码本身就不划算了**，置信度只能让损失小一些。

## 4. 那么高并发的部署为什么还开着投机解码

上面的模拟是一个 8B 的稠密模型，batch 到几百就受算力限制。大规模的 MoE 部署不同：

- **MoE 的激活参数少**。DeepSeek-V3 每个 token 只激活 370 亿参数，相同 batch 下的计算量远小于同样大小的稠密模型，更难受算力限制。
- **长上下文时，Attention 读 KV 占了大头**。验证多个草稿 token 时，它们读的是同一份 KV，额外的开销很小（3.5 节）。
- **Wide EP 下每张卡的 batch 有限**，MoE 部分仍然受带宽限制。

所以对 DeepSeek 这类模型，投机解码在每卡几十到上百的并发下仍然有收益，而置信度让它在负载变化时保持在最优附近。vLLM 在 V4.1-Flash 上的基准中，每个请求每步验证 1 个 token 加 5 个草稿。

> [!NOTE]
> 投机解码还会影响 6.7 节的确定性：草稿被接受多少，取决于这一步的 batch 组合，而接受多少又改变了后续每一步的 batch。DeepInfer 要求得到确定性采样时关闭投机解码，原因就在这里。

## 5. 实验

- **CPU**：在 `mtp_sim.py` 中把 `--noise` 调到 0.3，置信度相对于固定 $K$ 的优势还在吗？
- **CPU**：实现一个随 batch 自动调整阈值的策略（比如阈值 = 0.3 + 0.002 × batch），与固定阈值比较。
- **组件**：把 batch 从 1 逐步加大，记录最优的固定 $K$ 和最优阈值，画成两条曲线。
- **GPU**：用 vLLM 启动一个带 MTP 层的模型（如 Qwen3-Next 或 GLM-4.5-Air），分别设 `num_speculative_tokens` 为 1、2、3，在并发 1、16、64 下测 TPOT 和吞吐，并从日志中读出各位置的接受率。
