# 0.1 模型服务概览

> 对应原书第 1 章。

模型训练好之后，要接收真实用户的请求并返回结果，这一步叫**模型服务**（model serving）。对大语言模型来说，服务这一环往往比训练更花钱：训练是一次性的投入，服务则要按请求量持续付出 GPU 时间。

这一节先说明服务和训练的区别，再看一个模型由哪几部分组成、推理优化改的是哪一部分，然后介绍几种常见的部署形态。最后在 GPU 上用 vLLM 启动一个服务，读一读它的启动日志。

## 1. 从一段 generate() 代码说起

用 Hugging Face Transformers 让模型回答一个问题，只需要几行代码：

```python
from transformers import AutoModelForCausalLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-8B")
model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-8B", torch_dtype="bfloat16").cuda()
inputs = tok("请解释什么是 KV Cache", return_tensors="pt").to("cuda")
out = model.generate(**inputs, max_new_tokens=100)
print(tok.decode(out[0]))
```

自己用没有问题。但如果把它包进一个 HTTP 接口，让几十个人同时使用，很快会遇到三个问题。

**请求只能排队。** `generate()` 一次处理一个请求，或者一批事先凑好的请求，必须等整批生成结束才能接下一批。后来的用户要等前面的人生成完，才能看到第一个字。

**显存不可控。** 如果把多个请求拼成一批，批里最长的那个请求决定了显存占用。某个用户贴进来一篇长文档，整批就可能 OOM。

**GPU 大部分时间在等数据。** 逐个生成 token 时，每一步只为一个 token 做计算，却要把 16 GB 的权重从显存完整读一遍。算力单元大多在等读取，利用率往往只有个位数百分比。0.7 节会把这笔账算清楚。

推理引擎（vLLM、SGLang、TensorRT-LLM 等）做的事，就是解决这三个问题：让新请求随时加入正在运行的批，按需分配显存，把多个请求的计算合在一起摊薄读权重的开销。vLLM 首次发布时报告，在 LLaMA-7B 和 13B 上，它的吞吐是 Hugging Face Transformers 的 14～24 倍。这个差距不来自更快的硬件，也没有改动模型，全部来自执行方式的不同。

## 2. 训练和服务有什么不同

训练和服务运行的是同一个网络，但目标和约束差别很大：

| | 训练 | 服务 |
|---|---|---|
| 目标 | 降低损失，更新参数 | 在延迟要求内回答请求，成本尽量低 |
| 计算 | 前向、反向、优化器更新 | 只有前向，但要保存每个请求的 KV Cache |
| 输入 | 离线数据集，可以整齐地分成固定大小的批 | 请求随时到达，长度从几个 token 到几万个 token 不等 |
| 时间要求 | 看总吞吐，一次训练跑几天也可以 | 首个 token 通常要在 1 秒内返回，之后要连续输出 |
| 衡量标准 | 收敛速度、评测分数 | 延迟达标率、每张卡的吞吐、每百万 token 的成本 |

服务的难点集中在第三、四行：输入长度不可预测，又要求低延迟。后面的大部分内容，都是在这两个约束下想办法提高吞吐。

## 3. 一个模型由哪几部分组成

原书把一个可运行的模型拆成三部分：

| 部分 | 内容 | 以 Qwen3-8B 为例 |
|---|---|---|
| 模型结构 | 网络有多少层、每层怎么计算 | `config.json` 里的层数、隐藏维度、注意力头数等超参数 |
| 模型数据 | 训练得到的参数，以及分词器 | `*.safetensors` 权重文件、`tokenizer.json` |
| 执行代码 | 把结构和数据组织成实际的计算：怎样分批、怎样管理显存、调用哪些 GPU 算子 | Transformers 的 `modeling_qwen3.py`，或 vLLM、SGLang 中各自的实现 |

从 Hugging Face 下载模型，拿到的是前两部分。同一份权重可以交给不同的执行代码运行，结果在数学上相同，速度却可以差一个数量级。

推理优化大多发生在执行代码这一层：批处理与调度（第 1 部分）、注意力算子（第 3 部分）、多卡并行（第 4 部分）。量化（第 2 部分）是例外，它会改动模型数据，因此要额外评估精度。

项目 1 的 MiniServe 会加载 Qwen3 的官方权重，自己实现执行代码：一个带连续批处理和分页 KV Cache 的推理引擎。

## 4. 常见的部署形态

按模型数量和运行位置，原书把模型服务分成几类：

| 形态 | 特点 | 适用场景 |
|---|---|---|
| 端侧服务 | 模型运行在手机、笔记本、车机上，通常只服务一个用户 | 离线可用、数据不能出设备；模型要小，通常需要 4 位量化 |
| 单模型服务 | 一个服务只部署一个模型，独占 GPU，多副本扩展 | 流量集中在少数几个模型上，比如面向外部用户的对话产品 |
| 多模型服务 | 多个模型共享一组 GPU，按需加载、卸载 | 模型很多但单个模型流量低，比如为每个客户微调的模型 |
| 服务平台 | 在上面几种之上，提供部署、扩缩容、灰度、监控、配额等能力 | 公司内部统一的推理平台，或云厂商的托管服务 |

单模型服务最简单，也最容易把性能做到极致：所有显存都留给一个模型的权重和 KV Cache。多模型服务省的是空闲成本：1000 个每天只被调用几十次的模型，不可能每个都独占一张卡。如果这些模型都是在同一个基座上做的 LoRA 微调，还可以只加载一份基座权重，按请求切换 LoRA 适配器（4.7 节）。

## 5. 负载均衡：为什么轮询不够用

一个模型部署多个副本后，需要在前面放一个网关分发请求。普通 Web 服务常用轮询（round-robin），依次把请求发给每个副本。各个请求开销差不多时，这样分配很均匀。

LLM 请求的开销却相差很大。"你好"只有几个 token 的输入和十几个 token 的输出；"总结这份财报"可能有一万多个 token 的输入和上千个 token 的输出，计算量相差几百倍。轮询只看请求个数，不看请求大小，长请求一旦扎堆分到同一个副本，那里就会排起长队，而其他副本可能是空闲的。

下面的模拟中有 3 个副本，每个副本同一时刻只处理一个请求。请求大小服从长尾分布：大部分很小，少数很大。比较不同的分发策略下，请求的平均等待时间和尾部等待时间。

实际的 LLM 网关常用两类信息做决策：

- **副本当前的负载**：排队请求数、正在生成的 token 数、KV Cache 剩余空间。vLLM 等引擎都通过 `/metrics` 接口暴露这些指标。
- **前缀缓存的位置**：多轮对话的第 5 轮请求包含前 4 轮的全部内容。如果前 4 轮的 KV Cache 还留在某个副本的显存里，把请求发到那里就能跳过这部分计算。1.4 节介绍前缀缓存，4.6 节讨论怎样在网关上利用它。

## 6. 生产环境还要考虑什么

把服务交给真实用户之前，除了速度，通常还要考虑这些问题：

- **部署**：模型、驱动、推理引擎能否打包成镜像，在几分钟内拉起一个新副本。
- **扩展**：流量上涨时增加副本；单卡放不下模型时，在一台机器内用多卡张量并行。尽量避免把一个模型切到多台机器上，因为机间网络带宽比机内 NVLink 低一个数量级（0.5 节）。
- **延迟**：首个 token 的等待时间（TTFT）和之后每个 token 的间隔（TPOT）是否满足要求（0.8 节）。
- **监控**：能否看到排队长度、KV Cache 使用率、P99 延迟。
- **版本管理**：新模型能否先切一小部分流量试运行，出问题时能否快速回滚。
- **安全与隔离**：恶意的超长输入会不会耗尽显存；不同租户之间会不会通过缓存泄露信息（1.4 节）。
- **成本**：在以上要求都满足的前提下，每处理一百万个 token 花多少钱。这通常是比较两套方案的最终依据。

## 7. 实验：启动 vLLM 并读启动日志

在有 GPU 的机器上（安装见[实验环境](guide/lab-setup.md)），用一条命令启动一个 Qwen3-0.6B 的服务：

```bash
vllm serve Qwen/Qwen3-0.6B --max-model-len 4096 --gpu-memory-utilization 0.9
```

启动日志很长，其中有三行值得留意。在一张 24 GB 的卡上，它们大致是这样（具体数字随 vLLM 版本和显卡而变）：

```text
Model loading took 1.12 GiB and 4.3 seconds
GPU KV cache size: 177,872 tokens
Maximum concurrency for 4,096 tokens per request: 43.43x
```

| 日志 | 含义 | 在哪一节推导 |
|---|---|---|
| `Model loading took 1.12 GiB` | 权重占用的显存 | 0.6 节 |
| `GPU KV cache size: 177,872 tokens` | 扣除权重和运行时开销后，剩余显存能缓存多少个 token 的 K、V | 0.6 节、1.3 节 |
| `Maximum concurrency ... 43.43x` | 如果每个请求都用满 4096 个 token，最多能同时运行多少个请求 | 0.6 节 |

第三行就是第二行除以 4096。实际请求很少用满最大长度，所以真实的并发数通常比这个数字高。

服务启动后，在另一个终端发送一个请求：

```bash
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen/Qwen3-0.6B",
    "messages": [{"role": "user", "content": "用一句话解释什么是模型服务"}],
    "max_tokens": 64
  }'
```

这个接口和 OpenAI 的 Chat Completions 接口兼容。主流推理框架都提供这样的接口，因此换框架时，调用方通常不需要改代码（1.5 节）。
