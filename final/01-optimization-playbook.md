# 5.1 端到端优化流程

> 对应原书第 9 章 *LLM Optimization in Practice*。对实验结果的重新解读是书外内容。

前四部分讲了很多优化手段。真正动手优化一个服务时，问题变成了：从哪里开始，怎样知道一项改动有没有用，什么时候该停。原书第 9 章用 vLLM 部署 Qwen3-14B 作为例子，完整地走了一遍这个过程。这一节按原书的八个步骤展开，并对其中几个实验结果给出更准确的解释，因为正确地解读压测数据，本身就是优化中最重要的能力之一。

## 1. 先定目标

原书的目标是：最大化**单个模型实例的 token 吞吐**。每秒处理的 token 越多，单位 token 的成本越低，而 token 正是大多数 LLM 服务的计价单位。

原书同时提醒，吞吐和延迟在很多情况下可以同时改善（比如减少重复计算），但在某些负载下是矛盾的：提高吞吐依赖于把更多请求攒在一起处理，这会增加每个请求的等待；追求最低的延迟则要求请求一到就处理，硬件利用率随之下降。实际中的常见做法是：**在延迟可接受的前提下，尽量提高吞吐**。

目标定了，才能决定用什么负载、看什么指标、优先尝试什么。

## 2. 八个步骤

| 步骤 | 内容 | 本教程中的相关内容 |
|---|---|---|
| 1 | 了解硬件：显存、带宽、计算能力、卡间连接 | 0.5 节 |
| 2 | 构造有代表性的测试负载 | 0.8 节 |
| 3 | 定义评测指标 | 0.8 节 |
| 4 | 启动服务，确认显存和 KV Cache 的分配 | 0.6 节 |
| 5 | 用默认配置压测，建立基线 | |
| 6 | 换成量化模型，重新压测 | 第 2 部分 |
| 7 | 针对负载的类型尝试其他优化 | 第 1、3、4 部分 |
| 8 | 尝试多卡部署 | 4.1 节 |

### 步骤 1：硬件

原书在一台 AWS g6e.2xlarge 上做实验，它有一张 L40S（48 GB 显存，计算能力 8.9）。第一个命令总是 `nvidia-smi`：确认驱动和 CUDA 的版本与推理框架兼容；性能状态 P8 表示空闲，满载时应该是 P0 或 P1；显存的占用和总量。原书还提醒了两个常见的信号：负载下 GPU 利用率低，说明批处理或调度有问题；功耗高但吞吐低，说明受限于显存带宽或者 kernel 效率不高。

```bash
nvidia-smi --query-gpu=name,compute_cap,memory.free,memory.used,memory.total --format=csv
```

### 步骤 2：负载

原书强调，整个优化过程是在为某一类负载调参，所以测试数据必须反映实际的使用方式：以长输入为主（prefill 重）的负载和以长输出为主（decode 重）的负载，适合的策略完全不同。原书用了两个数据集：

- **ShareGPT**：真实的对话数据，输入、输出长度都比较均衡，模拟聊天场景；
- **Prefix Repetition**：合成数据，若干个固定的前缀加上不同的后缀，用来测试前缀缓存。

原书在 100 条 ShareGPT 样本上的统计：输入长度中位数 141.5、平均 232.6，输出长度中位数 164.5、平均 220.6，分布都有很长的尾巴。用 `vllm bench serve` 发送负载：

```bash
vllm bench serve --backend vllm --base-url http://localhost:8000 --model Qwen/Qwen3-14B \
  --dataset-name sharegpt --dataset-path ShareGPT_V3_unfiltered_cleaned_split.json \
  --num-prompts 2000 --request-rate 10 --max-concurrency 10 \
  --save-result --result-filename results.json
```

### 步骤 3：指标

原书表 9-1 列出了常用的指标：吞吐（总 token、输出 token、请求数）、延迟（TTFT、TPOT、ITL，看平均和 P99）、资源利用（GPU 利用率、显存）、负载画像（输入输出比、并发、请求速率）、可靠性与成本（错误率、成本效率）。原书的实验主要看四个：总 token 吞吐、输出 token 吞吐、平均 TTFT、平均 ITL。

### 步骤 4：启动服务

默认配置启动后，vLLM 的日志给出了显存的分配：

```text
Model loading took 27.5185 GiB and 5.265852 seconds
Available KV cache memory: 11.00 GiB
GPU KV cache size: 72,064 tokens
Maximum concurrency for 40,960 tokens per request: 1.76x
```

权重占了 27.5 GiB，留给 KV Cache 的只有 11 GiB。原书据此判断，KV Cache 的空间会限制批处理和并发，下一步应该用量化腾出显存。

### 步骤 5：基线

ShareGPT 负载、每秒 10 个请求、最大并发 10 的结果：总吞吐每秒 474 个 token，输出吞吐 227.6，平均 TTFT 104 ms，平均 ITL 43 ms。

Prefix Repetition 负载（10 个 256 token 的前缀、256 token 的后缀、128 token 的输出）的总吞吐是每秒 1123 个 token。原书把它解释为前缀缓存等机制复用了计算。

### 步骤 6：量化

换成 Qwen3-14B-AWQ 后，权重降到 9.4 GiB，KV Cache 能容纳的 token 从 72,064 增加到 191,056。ShareGPT 负载下总吞吐从 474 提高到 1280，约 2.7 倍；平均 TTFT 从 104 ms 降到 59 ms。

### 步骤 7：其他优化

原书按负载类型给出了方向：长上下文、prefill 重的负载，试试 LMCache 复用 KV（4.4 节）；长输出、decode 重的负载，试试投机解码（3.4、3.5 节）。然后才是调参数，比如 `--gpu-memory-utilization`、`--max-num-seqs`、`--max-num-batched-tokens`。

原书特别提醒**不要过度调参**：为某一种显卡或负载调到极致的配置，换一个环境可能表现很差甚至无法运行。现在的推理框架会根据硬件自动推断不错的默认值，大部分精力应该花在"选择用哪些优化手段"上，而不是追求完美的参数。

### 步骤 8：多卡

原书在 4 张 L40S（g6e.12xlarge，只有 PCIe）和 8 张 A100（p4d.24xlarge，有 NVLink）上分别测试了 TP = 1、2、4：L40S 上单卡最好，A100 上 4 卡最好。原因正是 4.1 节说的卡间连接。5.2 节会进一步讨论横向与纵向扩展的取舍。

## 3. 重新解读实验结果

原书的实验步骤是完整的，但有两处结果的解释值得推敲。

### 3.1 量化为什么快了 2.7 倍

原书把 AWQ 的收益归因于两点：KV Cache 变大，允许更大的批处理；以及"减少了 CPU 和 GPU 之间的数据传输"。

第二点在 2.3 节已经订正过：推理时权重一直在显存中，减少的是每一步从显存读权重的字节数。第一点在这个实验中**并不成立**。压测设置了 `--max-concurrency 10`，同时在途的请求最多 10 个，每个约 430 个 token，一共只需要约 4K token 的 KV，远小于默认配置的 72K。KV Cache 从来不是瓶颈，变大也不会让 batch 变大。

真正的原因可以用 Little 定律解释：并发固定时，吞吐 = 并发 ÷ 每个请求的耗时。每个请求的耗时主要是 decode，batch 只有 10 时 decode 受限于读权重的带宽：L40S 的带宽是 864 GB/s，读一遍 27.5 GB 的权重要 32 ms，这正是基线 ITL 43 ms 的主要部分；AWQ 的权重只有 9.4 GB，读一遍约 11 ms。ITL 下降，每个请求的耗时下降，吞吐就按同样的比例上升。

两种解释的区别在于它们指向不同的下一步。如果瓶颈是 KV Cache，应该继续压缩 KV、增加显存；如果瓶颈是并发上限，应该先放开 `--max-concurrency`，看系统在更高并发下的表现。原书的实验只测了并发 10 这一个点，没有回答"这张卡最多能承受多少负载"。更完整的做法是 2.7 节第 5 节的并发扫描。

### 3.2 前缀重复的负载为什么吞吐更高

原书比较的是**总** token 吞吐（输入加输出）：ShareGPT 474，Prefix Repetition 1123。但两者的**输出**吞吐几乎一样：227.6 和 223.3，平均 ITL 也几乎一样。

差别主要来自负载本身：Prefix Repetition 每个请求有 512 个输入 token、128 个输出 token，ShareGPT 平均约 223 个输入、206 个输出。并发同样是 10、decode 的速度相同时，每完成一个请求，前者"顺带"处理的输入 token 多得多，总吞吐自然更高。前缀缓存确实节省了这些输入的 prefill 计算，但在这个实验里，它对总吞吐的贡献远没有输入输出比例的差别大。

这提醒我们：**比较不同负载的总 token 吞吐没有意义**，要比较同一个负载在不同配置下的结果，并且同时看输出吞吐、TTFT 和 ITL。

### 3.3 原书配置示例中的问题

原书步骤 7 给出的调参示例有几处需要注意：

- `--max-paddings` 是早期 vLLM 的参数，现在的版本已经没有了，加上会导致启动失败。
- 示例的启动脚本中写了 `--max-num-seqs 8` 和 `--max-model-len 1024`：前者让 batch 最多只有 8 个请求，与"提高吞吐"的目标相反；后者小于 ShareGPT 中部分请求的输入加输出长度，这些请求会被拒绝。它们只能作为参数写法的示意，不是推荐的配置。
- `--quantization awq` 会强制使用较慢的老 kernel（2.3 节），`--enable-prefix-caching` 和 `--enable-chunked-prefill` 在 vLLM V1 中已经默认开启。

## 4. 一份检查清单

把原书的流程和本教程的内容合在一起：

1. **定目标**：吞吐优先还是延迟优先？SLO 是多少（TTFT、ITL 的 P99）？
2. **画像负载**：输入、输出长度的分布，前缀重复的程度，并发的范围。用真实的数据或者最接近的公开数据集。
3. **估算上限**：用 0.6、0.7 节的方法估算显存分配和带宽上限，心里先有一个"理论上能到多少"的数字。
4. **测基线**：默认配置，做并发扫描，记录吞吐、TTFT、ITL 随并发的曲线，找到满足 SLO 的最大并发。
5. **找瓶颈**：KV Cache 满了？decode 受限于带宽？prefill 拖慢了 decode？CPU 开销？用 3.6 节的方法确认。
6. **对症下药**：权重或 KV 太大，量化（第 2 部分）；prefill 干扰 decode，调 chunked prefill 或 PD 分离（1.2、4.3 节）；前缀重复多，确认缓存命中和路由（1.4、4.6 节）；输出长、并发低，投机解码（3.4 节）；模型放不下或延迟不够，多卡（4.1 节）。
7. **一次只改一处**，每次都在同一个负载下重新做并发扫描，和基线比较。
8. **验证精度**：量化、投机解码等改动后，确认质量没有退化（2.7 节）。
9. **适可而止**：收益低于测量误差、或者配置开始变得脆弱时，停下来。

## 5. 实验

- **CPU**：用项目 1 的 MiniServe 和 `bench.py` 完整地走一遍步骤 4 到 7：小模型、默认配置的基线，然后分别改变 `--max-num-batched-tokens` 和关闭 chunked prefill，做并发扫描。
- **组件**：在本节的组件中把并发上限调到 64，配置 A 和 B 的吞吐之比变了吗？为什么在真实系统中会变？（提示：并发升高后 ITL 会变化，而且两种配置变化的幅度不同。）
- **GPU**：在一张 24 GB 以上的卡上，用 Qwen3-8B 和 Qwen3-8B-AWQ 重复原书的步骤 5、6，但把 `--max-concurrency` 依次设为 10、32、64、128。2.7 倍的差距在高并发下还在吗？
