# 毕业项目：为一个业务设计推理服务

> 前置：全部六个部分，以及项目 1～4。规划工具在 [`code/graduation`](https://github.com/zrpxx/hands-on-llm-serving-opt/tree/main/code/graduation)，依赖项目 4 的模拟器，在 CPU 上几秒钟出结果。验证阶段有 GPU 时用 vLLM 或 SGLang，没有 GPU 时用项目 1 的 MiniServe 和小模型。

前面四个项目各自练一项能力：写一个推理引擎、做量化、写算子、模拟集群。实际工作中遇到的问题不是这样分开的。一个典型的任务是：业务方给出一个场景和一些约束，你要拿出一份方案，说明用什么模型、什么精度、多少张卡、怎样部署、怎样路由，预计能达到什么延迟、每百万 token 花多少钱，并且用实测证明它可行。

毕业项目就是完成这样一份方案。它没有标准答案，评价的是推理过程：每一个决定是否有数字支撑，估算与实测是否吻合，不吻合时是否找到了原因。

## 1. 选一个场景

从下面三个中选一个，也可以用你自己工作中的真实场景（不要包含内部数据）。

| 场景 | 负载特征 | 主要矛盾 | 相关章节 |
|---|---|---|---|
| **A. 多租户知识库问答** | 128 个企业客户，每个有 4K token 的系统提示词和文档；流量集中在少数大客户；峰值 48 请求/秒 | 前缀复用、路由、成本 | 1.4、4.6、5.1 |
| **B. 长文档分析** | 输入 2K～8K token，输出几百 token；峰值 4～8 请求/秒；用户对首字延迟敏感 | prefill 与 decode 的干扰、PD 分离 | 1.2、4.3、6.6 |
| **C. Agent 编程助手** | 每个会话 8～30 轮，上下文只增不减，工具调用之间有几秒间隔；输入与输出之比约 45 : 1 | 会话亲和、KV 保留、结构化输出 | 5.7、4.4、6.5 |

每个场景都要先写清楚三件事：

- **负载**：峰值的请求速率、输入和输出长度的分布、前缀共享的情况。
- **SLO**：TTFT 和 TPOT 的目标（用 P99 还是 P90），以及 goodput 的目标（比如 99% 的请求同时满足两项）。
- **约束**：可用的卡型、预算、模型质量的底线（量化后在业务评测集上的分数不能低于多少）。

## 2. 第一步：手算

不用任何工具，先用前几部分的公式估一遍。这一步的目的是建立预期，后面的模拟和实测要与它对照。

- **显存**（0.6 节）：权重多大，每个 token 的 KV 多大，一张卡能放多少 token 的 KV。
- **单步耗时**（0.7 节）：decode 一步的下限是多少，batch 多大时开始受算力限制。
- **需要多少并发**（5.1 节，Little 定律）：峰值速率乘以每个请求的平均耗时，就是同时在途的请求数。它能放进 KV Cache 吗？
- **前缀缓存能省多少**（1.4 节）：场景 A 和 C 中，命中率的理论上限是多少？

以场景 A 为例：Qwen3-8B 的 BF16 权重约 16 GB，每个 token 的 KV 约 144 KB，一张 H100 留给 KV 的显存能放 30 多万个 token。每个请求约 4.4K 输入、160 输出，如果每个请求耗时约 5 秒，峰值 48 请求/秒时同时在途约 240 个请求，KV 约 100 万个 token，不计前缀共享需要三四张卡。前缀命中时，4K 的公共部分只存一份，KV 的压力小得多，瓶颈转到算力上。

## 3. 第二步：用模拟器规划

`code/graduation/plan.py` 在项目 4 的模拟器上搜索方案：实例数、权重精度（BF16 或 FP8）、路由策略（最少负载或缓存感知）、部署方式（聚合或 PD 分离）。对每个方案计算 goodput，找出满足目标、卡数最少的几个。

```bash
python code/graduation/plan.py                          # 场景 A 的默认参数
python code/graduation/plan.py --workload long --rate 4  # 场景 B
python code/graduation/plan.py --ttft 0.5 --tpot 0.03    # 改变 SLO
```

场景 A 的部分输出：

```text
负载：多租户聊天，48.0 请求/秒；SLO：TTFT ≤ 1000 ms，TPOT ≤ 30 ms，goodput ≥ 99%

卡数  精度  路由      部署   goodput  TTFT P99  ITL P99  命中率  输出 token/s  $/百万 token
   2  FP8   缓存感知  聚合      0.01   3031 ms  92.5 ms   0.81          5742          0.24
   3  BF16  缓存感知  聚合      0.04    391 ms  97.3 ms   0.80          6217          0.34
   3  FP8   最少负载  聚合      0.24    304 ms  54.3 ms   0.62          6808          0.31
   3  FP8   缓存感知  聚合      1.00    125 ms  40.7 ms   0.79          7048          0.30  ✓
   4  BF16  缓存感知  聚合      1.00    206 ms  67.6 ms   0.82          6922          0.40  ✓
   4  FP8   最少负载  2P2D      0.38    178 ms  17.6 ms   0.60          5963          0.47

满足目标的最少卡数：3。可行的方案，按成本排序：
  3 张卡，FP8，缓存感知路由，聚合；每百万输出 token 约 $0.30
  4 张卡，FP8，缓存感知路由，聚合；每百万输出 token 约 $0.39
  ...
```

几个值得在报告中讨论的现象：

- **单看每 token 成本会选错**。2 张卡时成本最低（每百万输出 token 约 0.24 美元），但 goodput 只有 1%：卡被压满了，吞吐高，请求却在排队。成本必须在满足 SLO 的前提下比较。
- **3 张卡时，只有 FP8 加缓存感知路由能达标**。两项优化各自都不够：FP8 降低了每步的耗时，缓存感知路由提高了命中率、减少了 prefill。
- **PD 分离在这个场景中不合适**。输入的大部分是可以复用的前缀，真正要算的 prefill 很少；拆出的 prefill 实例用的是最少负载路由，命中率反而下降。场景 B 的结论会不同。

模拟器忽略了很多东西：量化对质量的影响、注意力的计算量、调度的 CPU 开销、网络抖动、故障。它的用处是**缩小搜索范围**，告诉你哪两三个方案值得在真实环境中验证。

## 4. 第三步：验证

**有 GPU 时**，部署模拟器选出的两三个方案，用与模拟相同的负载压测：

```bash
# 例：FP8 权重、开启前缀缓存的单个实例
vllm serve Qwen/Qwen3-8B-FP8 --enable-prefix-caching --max-num-batched-tokens 2048

# 用 vllm bench serve 压测；带共享前缀的负载可以用 --dataset-name prefix_repetition，
# 或者用 workload.py 生成请求后写成自定义数据集
vllm bench serve --model Qwen/Qwen3-8B-FP8 --dataset-name prefix_repetition \
  --request-rate 16 --num-prompts 1000 --percentile-metrics ttft,tpot,itl --metric-percentiles 50,90,99
```

多实例的路由可以用 SGLang Router 或 vLLM 的生产栈（4.6、4.8 节）。卡不够时，可以按比例缩小：用一张卡和 1/N 的请求速率验证单实例的行为，再由模拟器推算多实例的结果，并在报告中说明这一推算。

质量也要验证：在业务评测集（或 GSM8K、MMLU 这类公开基准的一个子集）上比较 BF16 与 FP8 的分数（2.7 节）。

**没有 GPU 时**，用项目 1 的 MiniServe 和一个小模型（Qwen3-0.6B，或项目 2 训练的小模型）在 CPU 上验证相对的结论：开关前缀缓存、改变 chunked prefill 的预算时，TTFT 和 ITL 的变化方向是否与模拟器一致。绝对数字不可比，变化的方向和大致的比例可以比。

**把实测与模拟放在一起**。对每个方案列出模拟与实测的 TTFT P99、ITL P99、吞吐，计算偏差。偏差超过 30% 时，找出原因：是耗时模型漏了什么（注意力的计算、CPU 开销），还是负载与假设不同（输出长度的分布、到达的突发性）。修改模拟器的参数，重新预测，看是否吻合。

## 5. 第四步：写方案

方案文档的结构：

1. **结论**：一段话，说明推荐的配置、它在什么负载下满足什么 SLO、成本是多少。
2. **场景与需求**：负载、SLO、约束，以及它们的来源。
3. **估算**：第一步的手算，以及它预测的瓶颈。
4. **备选方案与取舍**：模拟器的结果；被否决的方案以及否决的理由。
5. **验证**：实测的数据、与模拟的对比、偏差的分析；量化前后的质量对比。
6. **风险与预案**：流量超过峰值时会怎样（排队、降级、扩容需要多久，4.5 节的冷启动）；哪些假设如果不成立，方案需要修改。
7. **下一步**：还没有尝试、但可能有收益的优化（投机解码、FP4、更细的路由），以及验证它们需要什么。

报告中的每一个结论都要有数字。"缓存感知路由效果更好"不是结论；"缓存感知路由把命中率从 0.62 提高到 0.79，TTFT P99 从 304 ms 降到 125 ms"才是。

## 6. 完成标准

- 一份完整的方案文档，包含上面七个部分。
- 手算、模拟、实测三组数字，以及它们之间的对比和分析。
- 至少一个被否决的方案，以及否决它的数据。
- 至少一处模拟与实测不吻合的地方，以及你找到的原因。
- 量化前后的质量对比（如果方案用了量化）。
- 用于复现的命令和脚本。

## 7. 评审时会问的问题

写完以后，用这些问题检查自己的方案：

- 峰值流量翻倍时，哪个指标先崩溃？还有多少余量？
- 如果业务方把 TTFT 的目标从 1 秒收紧到 300 毫秒，方案要怎样改？成本增加多少？
- 前缀命中率的假设从哪里来？如果实际只有一半，方案还成立吗？
- 为什么不用更多的卡换更低的延迟？为什么不用更少的卡？
- 一个实例故障时，其余实例能承接它的流量吗？前缀缓存的命中率会怎样变化？
- 方案中哪一个数字你最没有把握？怎样尽快验证它？
