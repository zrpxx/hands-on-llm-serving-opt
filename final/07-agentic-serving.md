# 5.7 Agent 场景下的推理服务

> 对应原书第 4 章 *Model Serving in an Agentic World*。Agent 负载的特征分析、路由实验和工程建议是书外内容。

原书第 4 章指出，越来越多的 LLM 应用把模型嵌入到 Agent 系统中：模型不再是每个请求调用一次，而是在一个控制循环中被反复调用，检索信息、推理中间结果、执行工具、改进输出，最后才给出答案。原书认为这从根本上改变了对推理服务的要求。这一节分析 Agent 负载与普通聊天负载有什么不同，以及推理服务该怎样应对。

## 1. Agent 怎样使用模型

原书把 Agent 定义为一个由 LLM 驱动的自主系统，能够理解高层的目标、推理如何实现、选择并调用外部的工具和数据源、根据中间结果调整，最终在很少或没有人工干预的情况下完成任务。

Agent 的核心能力是**工具调用**，原书把它概括为四步：

1. LLM 根据用户的请求和可用的工具进行推理；
2. 生成结构化的输出（通常是 JSON），包含所选工具需要的参数；
3. Agent 执行这个工具调用；
4. 结果送回给 LLM，循环往复，直到任务完成。

一个 Agent 系统除了 LLM，通常还用到嵌入模型（检索）、视觉或语音模型、专门任务的小模型，以及各种外部 API 和数据库。它们都通过推理服务的接口被调用。原书强调，由于 Agent 往往是交互式、实时的，低延迟、高效率的推理服务对它的成败至关重要。

## 2. Agent 负载的特点

与一问一答的聊天相比，Agent 的负载有几个鲜明的特点：

- **一次任务，多次调用**。一个用户请求可能触发几十次 LLM 调用。每次调用的延迟会累加，端到端的耗时远长于聊天。
- **上下文只增不减**。每一轮都把之前的全部历史（系统提示词、工具定义、之前的所有调用和结果）发给模型，再追加新的工具结果。上下文越来越长。
- **输入远多于输出**。每轮的输出只是一个工具调用，几十到几百个 token；输入却是整个历史。输入与输出之比常常达到几十比一，甚至上百比一。
- **调用之间有间隔**。两轮之间要执行工具：查数据库、跑代码、访问网页，从几百毫秒到几分钟不等。
- **输出要符合格式**。工具调用必须是合法的 JSON，参数要符合工具的定义。

## 3. 前缀缓存是关键

所以对 Agent 负载来说，**前缀缓存的命中率几乎决定了一切**：TTFT、成本、能承载的并发。有 Agent 产品团队（如 Manus）明确地说，KV Cache 的命中率是他们最看重的一个指标。要让缓存真正命中，需要推理服务和应用两边配合。

### 3.1 推理服务这一边

**同一个会话的请求要落到同一个实例上。** 前缀缓存是每个实例本地的（4.6 节），如果一个会话的第二轮被路由到了另一个实例，前面的缓存就白费了。`code/stage5/agent_sessions.py` 用项目 4 的模拟器验证了这一点：

```bash
python code/stage5/agent_sessions.py
```

```text
4 个 H100 实例，Qwen3-8B；60 个 Agent 会话，每个 8 到 30 轮，系统提示词 4000 token

策略            命中率  TTFT P50  TTFT P99  ITL P99
轮询             0.28     212 ms     668 ms    59 ms
最少负载         0.29     214 ms     644 ms    59 ms
会话亲和         0.79      28 ms     692 ms    60 ms
缓存感知         0.92      26 ms     119 ms    11 ms

输入 token 与输出 token 之比：45 : 1
```

轮询和最少负载的命中率不到 0.3，TTFT 的中位数超过 200 毫秒。按会话做一致性哈希（会话亲和）后，命中率提高到 0.79，中位数降到 28 毫秒，但几个长会话集中的实例负载过重，P99 没有改善。缓存感知路由兼顾了命中率和均衡，P99 也降到了 119 毫秒；不必重算的长上下文少了，decode 被 prefill 打断的情况也少了，ITL 的 P99 从 59 毫秒降到 11 毫秒。

**两轮之间，缓存不能被淘汰。** 工具执行期间，这个会话没有活跃的请求，它的 KV 块引用计数为 0，在 LRU 中会被逐渐挤到前面。如果工具执行了几分钟，而期间有大量其他请求，缓存很可能已经被淘汰。可以做的有：给缓存留更多的显存；把 KV 卸载到 CPU 内存而不是直接丢弃（4.4 节）；根据会话的状态调整淘汰的优先级，正在等工具结果的会话优先保留。

### 3.2 应用这一边

前缀缓存要求 token **完全相同**。应用的一些看似无害的做法会让它失效：

- **在系统提示词的开头放时间戳**。每一轮的第一个块都不同，后面的一切都无法命中。
- **改写历史**。比如为了节省上下文，删掉或压缩之前的工具结果。被改动的位置之后的缓存全部失效。如果确实需要压缩，尽量集中在少数几次，而不是每轮都改。
- **序列化不稳定**。同一个工具定义或参数，每次生成的 JSON 键的顺序不同，token 就不同。
- **动态增删工具**。工具定义通常放在提示词的前部，改动它会让后面的缓存全部失效。可以保持工具列表不变，用其他方式（比如在采样时屏蔽）限制模型能选的工具。

使用第三方 API 时，这些做法同样决定了成本：缓存命中的输入通常只有普通输入价格的十分之一左右（4.4 节）。

## 4. 结构化输出

工具调用必须是合法的 JSON。靠提示词约束模型的输出格式并不可靠，推理引擎提供了**约束解码**：在每一步采样之前，根据 JSON Schema 或语法计算出哪些 token 是合法的，把其他 token 的概率置零。这样生成的结果一定符合格式。

vLLM、SGLang 都内置了约束解码，常用的后端是 XGrammar 等。它的开销主要在每一步计算合法 token 的掩码，好的实现会把这部分与 GPU 的计算重叠。在 vLLM 中使用工具调用，还需要指定模型对应的解析器：

```bash
vllm serve Qwen/Qwen3-8B --enable-auto-tool-choice --tool-call-parser hermes
```

## 5. 降低端到端的延迟

Agent 的端到端延迟是多次调用的累加，每一次的 TTFT 都会计入。几个方向：

- **前缀缓存**：上面讨论过，它对每一轮的 TTFT 影响最大。
- **投机解码**：原书在 3.5 节的讨论中提到，函数调用这类高度可预测的输出，草稿长度可以设得很大。工具调用的参数常常直接复制上下文中的内容，n-gram 方法效果很好。
- **并行的工具调用**：模型在一轮中同时请求多个互不依赖的工具，应用并行执行，减少轮数。
- **用合适的模型**：不是每一步都需要最强的模型，简单的步骤可以交给更快、更便宜的模型（5.3 节的模型路由）。
- **多 Agent 共享前缀**：多个子 Agent 从同一个上下文分叉出去时，共享的部分只需要计算一次。SGLang 的 RadixAttention 天然支持这种树状的共享。

## 6. 实验

- **CPU**：修改 `agent_sessions.py`，在每一轮的系统提示词中加入一个时间戳（让每轮的第一个块都不同，可以把 `prefix_len` 设为 0），重新运行，比较命中率。
- **CPU**：把工具执行时间改为 30 到 120 秒，缓存感知路由的命中率会怎样变化？为什么？
- **组件**：在本节的组件中，把轮数调到 50、工具结果调到 2000 token，有无前缀缓存的计算量相差多少倍？
- **GPU**：用 vLLM 启动 Qwen3-8B，写一个简单的多轮工具调用循环（工具可以是一个返回固定文本的假函数），观察 `/metrics` 中前缀缓存的命中率随轮数的变化。
