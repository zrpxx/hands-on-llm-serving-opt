# 4.6 负载均衡与缓存感知路由

> 对应原书第 7 章 *Data Parallelism* 中的路由策略，以及第 6 章 *Scaling Prefix Cache*。SGLang、llm-d、Dynamo 的路由器实现是书外内容。

数据并行（4.1 节）是最常用的扩展方式：部署多个相同的实例，前面放一个路由器。在传统的 Web 服务里，负载均衡是个早已解决的问题，轮询或者最少连接就够了。LLM 服务不一样：请求的长短可以相差几百倍，前缀缓存又是每个实例本地的，同一个请求发到不同的实例，处理的代价可能差十倍。原书认为，正因为 LLM 的负载差异大、硬件又昂贵，一个好的路由器带来的价值比传统 Web 应用中大得多。

## 1. 常见的策略

原书列出了四种策略：

| 策略 | 做法 | 问题 |
|---|---|---|
| 轮询 | 按固定顺序依次分配 | 不看负载。有的请求很长，有的实例会积压，有的闲着 |
| 最少连接 | 分给当前连接数最少的实例 | 只数请求的个数，不看每个请求有多长 |
| 基于延迟 | 分给最近响应最快的实例 | 能适应性能的波动，降低长尾 |
| 缓存感知 | 分给已经缓存了这个请求前缀的实例 | 要知道各实例缓存了什么，还要防止负载失衡 |

对 LLM 来说，"负载"不应该按请求个数算，而应该按要处理的 token 数算：一个 8K 输入的请求和一个 100 token 的请求，工作量差了几十倍。

原书还列出了 LLM 路由器可以利用的实时信号：

- KV Cache 的位置，以及每个实例上能命中的前缀长度占比；
- 每个实例的 KV Cache 使用率；
- 请求的输入长度；
- 每个实例排队等待的请求数、正在处理的请求数、这些请求已经生成的 token 数；
- 请求的 SLA，即它能容忍的最长响应时间。

## 2. 为什么要感知缓存

前缀缓存（1.4 节）是每个实例本地的。假设有 4 个实例、128 个租户，每个租户有一个 4K token 的固定前缀（系统提示词加上知识文档）。轮询会把同一个租户的请求分散到所有实例上，每个实例都要缓存全部 128 个前缀，显存放不下，就不断淘汰、重算。如果同一个租户的请求总是去同一个实例，每个实例只需要缓存四分之一的前缀，命中率会高得多。

原书第 6 章把这个思路和**一致性哈希**联系起来：在前缀和实例之间建立一种亲和关系，让相同前缀的请求总是落到同一个实例上。这样，并不是每个实例都需要缓存所有的前缀，节省了显存，也避免了不断的淘汰和重算。

但一致性哈希有一个问题：它不看负载。热门租户的请求全部落在同一个实例上，这个实例会被压垮。所以实际的缓存感知路由器都要在**命中率**和**负载均衡**之间取舍。

## 3. 实验：四种策略的延迟

项目 4 的模拟器把同样的负载放到 4 个 H100 实例上，统计延迟：

```bash
cd code/project4
CLUSTER_IMPL=solution python run.py routers
```

```text
4 个实例，128 个租户，每个前缀 4096 token，32 请求/秒，共 2000 个请求

策略            命中率  TTFT P50  TTFT P99  ITL P99   各实例的请求数
轮询             0.58     65 ms    327 ms  66.0 ms   [500, 500, 500, 500]
最少负载         0.57     31 ms    247 ms  65.5 ms   [501, 486, 509, 504]
一致性哈希       0.83     22 ms    255 ms  61.8 ms   [546, 403, 588, 463]
缓存感知         0.83     23 ms    169 ms  60.6 ms   [418, 436, 468, 678]
```

- 轮询和最少负载的命中率只有约 0.58；按前缀路由的两种策略都达到 0.83，需要实际计算的 prefill token 减少了约 60%。
- 命中率提高后，TTFT 的中位数从 65 毫秒降到 22 毫秒。
- 一致性哈希的 P99 不如缓存感知：它把请求固定地分给实例，各实例收到的请求数从 403 到 588 不等，热门租户所在的实例排队更长。缓存感知路由在负载接近时追随缓存，失衡时改按负载分配，P99 最低。

## 4. 生产中的实现

### 4.1 SGLang 的路由器

SGLang 的路由器（`sglang_router`）提供了缓存感知的策略。它不需要实例报告自己的缓存内容，而是在路由器内部为每个实例维护一棵**近似的前缀树**：把发给这个实例的请求文本插入它的树中，以此估计这个实例缓存了什么。新请求到来时：

- 如果各实例的负载是均衡的，选择前缀匹配最长的实例；匹配率低于阈值（`--cache-threshold`）时，选择缓存最少的实例，让新前缀均匀分布；
- 如果负载已经失衡（由 `--balance-abs-threshold` 和 `--balance-rel-threshold` 判断），忽略缓存，直接选负载最低的实例。

项目 4 的 `CacheAware` 就是按照这个思路实现的。

### 4.2 llm-d 与 Dynamo

**llm-d** 是建立在 Kubernetes 上的分布式推理框架。它的调度器对每个候选实例计算若干个分数，比如前缀缓存的命中程度、KV Cache 的使用率、队列长度，再按配置的权重加权，选总分最高的实例。原书推荐阅读它的路由器文档。

**NVIDIA Dynamo** 的 KV 路由器则让各个实例主动上报 KV 块的创建和淘汰事件，在路由器中维护一份全局的前缀索引，因此知道的是各实例**真实**的缓存内容，而不是估计。它综合考虑能命中的块数和每个实例当前的负载，计算一个代价，选择代价最小的实例。

两者都支持 PD 分离的路由（4.3 节）和 KV 卸载（4.4 节）。

## 5. 多租户的隔离

前缀缓存在多租户的场景下有一个安全隐患，原书专门提到了这一点：如果租户 A 和租户 B 的请求恰好有相同的前缀，B 的请求会命中 A 留下的缓存，响应更快。攻击者可以构造不同的前缀，通过观察响应的快慢来推测其他租户的输入内容。

原书引用了 NVIDIA 的建议：在提示词中插入每个租户（或会话）唯一的 ID，放在系统提示词之后、租户自己的内容之前。这样不同租户之间只能共享系统提示词这一段公共前缀，私有的内容不会跨租户命中：

```text
<system>
You are a helpful assistant.
<id> {租户 ID 或会话 ID}
<context>
Document: {租户自己的固定内容}
<user>
{用户的问题}
```

vLLM 也支持在请求中指定一个 `cache_salt`，把它混入前缀块的哈希中，效果相同，而且不需要改动提示词。

## 6. 实验

- **CPU**：在组件中把"每个实例能缓存的前缀数"调到大于租户数，四种策略的命中率变得一样。为什么？这说明在什么情况下不需要缓存感知的路由？
- **CPU**：运行 `run.py routers --tenants 16`，再运行 `--tenants 512`。缓存感知相对轮询的优势在哪种情况下最大？
- **CPU**：修改项目 4 的 `CacheAware`，用 `num_requests()` 代替 `queued_tokens()` 作为负载，比较 TTFT P99。
- **GPU（2 张卡）**：用 `sglang_router` 启动两个 SGLang 实例，分别以 `--policy round_robin` 和 `--policy cache_aware` 运行带共享前缀的负载，比较缓存命中率和 TTFT。
