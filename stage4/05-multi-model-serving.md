# 4.5 多模型服务

> 对应原书第 3 章 *Build a Multi-Model Serving Service from Scratch*、*Trade-offs in Multi-Model Serving Designs*，以及第 4 章的模型选择与编排层。vLLM 的睡眠模式和冷启动的估算是书外内容。

前面的讨论都假设一个服务只运行一个模型。实际中常常不是这样：一个平台可能要同时提供几种尺寸的模型、几个版本、若干个微调模型，还有嵌入模型、重排模型。给每个模型单独部署一组 GPU，流量小的模型会让 GPU 长期闲置；把多个模型挤在同一批 GPU 上，又会遇到加载慢、互相抢资源的问题。这一节讨论多模型服务的设计取舍。

## 1. 一个多模型服务由什么组成

原书第 3 章从零实现了一个多模型服务，它有五个组件：

| 组件 | 职责 |
|---|---|
| API 服务 | 提供统一的 HTTP 接口，请求中指定模型 ID |
| 模型管理器 | 维护已加载模型的缓存，协调模型实例的生命周期 |
| 模型仓库 | 保存模型的元数据：存放位置、框架、需要的资源 |
| 模型引擎 | 根据元数据创建对应的模型实例 |
| 模型实例 | 把模型加载进内存，执行推理 |

请求的处理流程是：API 服务收到请求，交给模型管理器；如果模型已经加载，直接转给对应的实例；如果没有，从模型仓库读取元数据，由模型引擎创建实例、加载模型，必要时按 LRU 淘汰一个最久未使用的模型，腾出资源。

这个设计的核心是**按需加载**加上**有上限的模型缓存**。原书举的例子是：给 1000 个客户各训练了一个模型，但它们不会同时被使用，可以限制同时最多加载 200 个，其余的在请求到来时再加载。

## 2. 两个难题

原书指出，多模型服务省成本的好处很明显，但有两个影响用户体验的难题：

- **冷启动**。请求的模型没有加载时，要下载权重、加载进显存，可能还要先淘汰别的模型。这需要几秒到几十秒，高峰时多个模型同时冷启动，会造成超时和连锁故障。
- **热门模型的扩展**。某个模型的流量突然增大时，要把它复制到更多的实例上，并更新路由。但每个实例都有自己独立的模型缓存，扩展起来很复杂，性能的表现也不容易预测。

### 2.1 模型缓存的容量

冷启动的代价有多大，取决于缓存能否装下常用的模型。`code/stage4/model_cache_sim.py` 模拟了 30 个模型共用一组 GPU 的情况，每张卡最多同时放两个模型，按 LRU 换入换出：

```bash
python code/stage4/model_cache_sim.py
```

```text
30 个模型，流量按 Zipf(1.2) 分布，合计 2.0 请求/秒；加载一个模型 20.0 秒，处理一个请求 0.2 秒

配置                     冷启动比例    延迟 P50    延迟 P99
共享： 4 张卡 × 每卡 2 个模型    36.4%   3416.3s   6767.2s
共享： 6 张卡 × 每卡 2 个模型    25.0%    906.2s   1795.5s
共享： 8 张卡 × 每卡 2 个模型    17.1%     15.9s     45.7s
共享：12 张卡 × 每卡 2 个模型     6.1%      0.2s     20.2s
专属：每个模型一张卡              0.0%      0.2s     约 0.2  （需要 30 张卡）
```

结果说明了共享模式的一个危险：**容量不够时，系统会崩溃，而不是平滑地变慢**。卡太少时，冷启动的比例很高，每次冷启动都要占用一张卡 20 秒，处理不了的请求越积越多，延迟变成几千秒。卡数增加到一定程度后，常用的模型都能常驻，冷启动只发生在冷门模型上，延迟迅速回到正常水平。12 张卡的共享方案用不到专属方案一半的 GPU，就让中位数延迟与专属方案相同，代价是 P99 被偶尔的冷启动拉长到 20 秒。

## 3. 两种设计

原书给出了两种设计，分别针对成本和延迟。

**成本优先**（原书图 3-11）：所有模型共用一组多模型实例，每个实例内部按需加载、按 LRU 淘汰。前面有一个路由层，维护"模型在哪些实例上"的映射：

- 尽量把请求发给已经加载了这个模型的实例，减少冷启动；
- 记录每个模型的副本数，热门模型复制到更多实例上；
- 用装箱的思路把模型集中到尽量少的机器上，节省资源。

它的问题是被动：总是在流量出现之后才调整，流量突然增大时延迟不可避免地上升；路由、扩缩、缓存状态的管理也让系统复杂、难以调试。

**延迟优先**（原书图 3-12）：每个模型有自己专属的实例组，提前通过一个配置服务创建好，不按需加载。路由层只需要把请求转发到对应的实例组。没有冷启动，各模型独立扩缩，也更容易运维。代价是成本：很难预测哪些模型会有大流量，常常会给流量很小的模型分配过多的资源。

原书的结论是：没有一种设计适合所有情况，要根据成本、性能、运维的优先级来选择。实际中常常是两者的组合：头部的少数模型用专属实例，长尾的大量模型共用一个池。

## 4. LLM 的多模型服务

LLM 通常按单模型的方式部署，因为它占用的资源太大。但原书指出，多模型的思路在 LLM 中依然有用，体现在三个地方：

- **前缀感知的路由**：把具有相同前缀的请求发给已经缓存了它的实例，和"把请求发给已经加载了模型的实例"是同一个思路（4.6 节）；
- **Multi-LoRA**：同一个基座模型上动态加载大量的 LoRA 适配器，每个适配器相当于一个微调模型，但切换的成本极低（4.7 节）；
- **模型的选择与编排**（原书第 4 章）：不是每个请求都需要最大的模型。一个路由层根据请求的难度，在大小模型之间选择，平衡效果、延迟和成本。原书举的例子是 OpenAI 默认使用较小的模型，用户明确要求时才用更强的模型。

### 4.1 降低 LLM 的切换成本

如果确实要在同一批 GPU 上轮换多个 LLM，可以从这几个方面降低切换的成本：

- **权重放在离 GPU 近的地方**：本地 NVMe、CPU 内存的页缓存，或者使用专门的流式加载工具，边读边往 GPU 传；
- **编译缓存**：`torch.compile` 的结果可以缓存到磁盘，第二次启动时直接使用；
- **睡眠模式**：vLLM 的 `--enable-sleep-mode` 允许把一个运行中的实例"睡眠"：一级睡眠把权重暂存到 CPU 内存、丢弃 KV Cache，释放显存；唤醒时把权重拷回即可，不用重新启动进程、编译和录制 CUDA Graph。它最初是为强化学习中推理与训练轮流使用 GPU 设计的（5.6 节），也适用于模型轮换。

```bash
vllm serve Qwen/Qwen3-8B --enable-sleep-mode
# 让出显存
curl -X POST "http://localhost:8000/sleep?level=1"
# 恢复
curl -X POST "http://localhost:8000/wake_up"
```

睡眠和唤醒的接口属于开发模式的功能，具体的启用方式以所用版本的文档为准。

## 5. 实验

- **CPU**：修改 `model_cache_sim.py` 的 `--zipf` 和 `--slots`，看流量越集中（Zipf 参数越大）、每卡能放的模型越多，需要的卡数怎样变化。再把 `--load` 从 20 秒降到 2 秒（相当于用了睡眠模式），重新运行。
- **CPU**：给 `simulate` 加一个"头部模型常驻"的选项：流量最大的 3 个模型各占一张专属的卡，其余模型共用剩下的卡。与纯共享方案比较 P99。
- **GPU**：在一张 80 GB 的卡上用 `--gpu-memory-utilization 0.45` 启动两个 Qwen3-8B 的 vLLM 实例，分别压测，观察它们的 KV Cache 容量和吞吐与单独占用整张卡时的差别。
